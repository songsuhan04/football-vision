# 축구 영상 → 2D 히트맵 · 전술 분석 웹 (Colab + 로컬 Next.js)

## Context

축구 영상에서 선수 움직임을 **바둑판 격자 2D 히트맵 + 이동 궤적**으로 시각화하고,
**AI가 선수별 움직임과 팀 전술을 자연어로 분석**해주는 웹 도구를 만든다.

**용도: 팀 전력분석 (내부 사용).** 공개 서비스가 아니다. → 로컬 실행 중심, 원본 영상은 배포물에 넣지 않는다.

### 2단계 전략 — 이 순서가 핵심이다

| 단계 | 영상 | 목적 |
|---|---|---|
| **Stage 1 (데모)** | **해외 프로 중계 영상** | Roboflow 모델의 **학습 도메인**이라 정확도가 보장된다. 여기서 **파이프라인과 웹을 완성**한다 |
| **Stage 2 (실사용)** | **직접 촬영한 아마추어 리그 영상** (높은 위치, 공을 따라 팬하는 "pitch view", 유니폼 통일) | 실제 전력분석 대상 |

**왜 이 순서인가:** 아마추어 영상으로 바로 시작하면 문제가 터졌을 때 *"코드가 틀렸나, 영상이 어려운가"* 를 구분할 수 없어
디버깅이 발산한다. 모델이 잘 되는 조건에서 먼저 완성해두면, Stage 2로 옮길 때 **남는 문제가 CV 정확도 하나로 좁혀진다.**

### Stage 1 → Stage 2 전환 비용

| 항목 | 비용 |
|---|---|
| **웹 전체** (히트맵·궤적·레이더·라벨링·AI 리포트) | **0 — 그대로 재사용** |
| 데이터 계약 / JSON 스키마 | 0 |
| 파이프라인 구조 (탐지 → 키포인트 → H → 추적 → 지표) | 0 |
| 프레임별 호모그래피 + 스무딩 | 0 — 중계도 팬·줌하므로 어차피 필요 |
| 컷 감지 on/off, 팀 분류 임계값, 구장 규격 | 낮음 — **프리셋 전환** (아래) |
| **모델 정확도** (저각도·좁은 화각에서 키포인트율 하락) | **★ 전환 비용의 90%.** 임계값 조정 → 광학 흐름 전파 → 필요시 파인튜닝(반나절~2일) |

### 전환을 싸게 만드는 장치: 소스 프리셋

컷 감지 여부·키포인트 임계값·스무딩 강도·탐지 임계값·구장 규격을 **하드코딩하지 않고 프리셋으로 묶는다.**

```python
# notebook/pipeline/presets.py
PRESETS = {
  "broadcast": {           # Stage 1 — 해외 프로 중계
    "cut_detection": True,        # 3~8초마다 컷, 리플레이·클로즈업 혼입
    "min_keypoints": 4,
    "min_players": 6,             # 클로즈업·관중샷 필터 (가장 강력)
    "min_window_s": 8,
    "h_smooth_window": 5,         # 팬·줌 있으나 카메라가 안정적
    "det_conf": 0.30,
    "pitch": (105, 68),
  },
  "handheld_elevated": {   # Stage 2 — 스마트폰 높은 위치 pitch view
    "cut_detection": False,       # 통짜 촬영 → 컷 없음
    "min_keypoints": 4,
    "min_players": 6,
    "min_window_s": 8,
    "h_smooth_window": 11,        # 손떨림 → 스무딩 강화
    "det_conf": 0.20,             # 먼 쪽 작은 선수 대응 → 임계값 하향
    "pitch": (100, 64),           # 아마추어 구장 실측값
  },
}
```

데이터 계약에 `source_profile` 을 기록해 웹이 신뢰도를 표시할 수 있게 한다. **웹은 소스 종류를 몰라도 되게 유지한다.**

### 아키텍처 결정: Colab(연산) + 로컬 Next.js(웹), 파일로 연결

영상 분석은 프레임마다 AI 모델 3개를 통과시키는 GPU 연산이다. 맥에서 돌리면 느리고 4GB 넘는 의존성이 깔린다.
연산은 **Google Colab 무료 T4 GPU**에서 하고, 웹은 순수 Next.js로 로컬에서 띄운다.

**Colab은 서버가 아니다** — 90분 유휴 / 최대 12시간에 세션 종료, 런타임 재시작 시 환경 소멸, 고정 URL 없음, 무료 티어 GPU 미보장.
따라서 웹이 Colab을 실시간 호출하는 구조(ngrok 터널)는 **쓰지 않는다**. 세션이 죽으면 웹도 죽는다.

대신 **파일 하나로 연결한다:**

```
[Colab 노트북 · T4 GPU]                            [웹 · npm run dev]
영상 → CV 파이프라인 → analysis-bundle.json  ──▶  드래그앤드롭
                                                    │
                        원본영상 ↔ 레이더 동기화 · 히트맵 · 궤적 · 라벨링 · AI 리포트
```

`analysis-bundle.json` **한 파일이 자기완결적**이다 — 좌표·지표·라벨링용 썸네일(base64)까지 전부 담는다.
웹은 파일을 받으면 백엔드 없이 전부 렌더링한다 (AI 리포트만 서버 라우트).

| 얻는 것 | |
|---|---|
| 내 맥 저장공간 | **~500MB** — Python 의존성 4GB가 맥에 없다 |
| 처리 속도 | 30초 구간 **20~40초** (T4). Mac MPS 대비 5~10배 |
| 개발 | 웹/CV 완전 분리 → 병렬 진행 |
| 대가 | 자동화 없음. 노트북 셀 수동 실행 (내부 도구라 수용) |

### 실행·배포 방식 — 로컬 중심 (전력분석 내부 사용)

공개 서비스가 아니므로 **`npm run dev` 로 로컬에서 띄우는 것이 기본**이다. 여기서 따라오는 이득:

- **동기화 재생용 영상에 용량 제약이 없다** — Vercel 100MB 제한을 신경 쓸 필요 없이 원본 화질 그대로 `web/public/` 에 둔다
- 발표 때는 화면 공유로 보여준다 (재배포가 아니다)
- `.gitignore` 에 `web/public/videos/` 를 넣어 **영상이 git에 올라가지 않게 한다** — 이게 저작권 안전선이다

**Vercel 배포는 선택 사항**이다. 하려면 원본 영상을 제외하고 `analysis-bundle.json` 만 담아 올린다.

> 저작권: 원본 중계 영상을 재배포하지 않고 내부 분석에만 쓰는 전제로 설계한다.
> (한국 저작권법상 사적이용 범위의 법적 판단은 이 계획의 범위 밖이다.)

### 내 맥에 실제로 다운받는 것

**원본 영상은 Colab이 받아 Colab에서 처리한다.** 맥에는 분석 결과와, 동기화 재생용 구간 클립만 온다.

| 맥에 있는 것 | 용량 |
|---|---|
| Next.js 프로젝트 + `node_modules` | ~500MB |
| `analysis-bundle.json` (Colab에서 받는 결과) | ~6MB |
| `notebook/` 소스 (.ipynb + .py) | ~100KB |
| 동기화 재생용 구간 클립 (분석 구간만, git 제외) | 구간당 20~100MB |
| **원본 영상 풀사이즈 (90분)** | **0** ← Colab에만 존재 |
| **PyTorch / OpenCV / 모델 가중치** | **0** ← Colab에만 존재 |

Phase 0 검증용 오버레이 영상도 **Colab 노트북 안에서 인라인 재생**하므로 다운로드하지 않는다.

파이프라인 로직을 노트북 셀에 인라인으로 쓰지 않는다 — 세션이 죽으면 코드까지 날아가고 버전 관리가 안 된다.
**리포는 private 으로 만든다** (영상은 어차피 `.gitignore`).

## 두 소스의 트레이드오프 (설계를 좌우함)

| | **Stage 1 · 프로 중계** | **Stage 2 · 스마트폰 pitch view** |
|---|---|---|
| 모델 적합도 | ✅ **학습 도메인 그 자체** — 탐지·키포인트 모두 잘 나옴 | ⚠️ **도메인 불일치** — 낮고 좁은 화각, 원근 극단적, 먼 쪽 선수가 몇 픽셀 |
| 컷 | ⚠️ 3~8초마다 컷, 리플레이·클로즈업·관중샷 대량 혼입 | ✅ **컷 없음** — 통짜 촬영 |
| 화각 | ✅ 메인캠 롱샷은 랜드마크가 충분히 보임 | ⚠️ **공을 따라 팬하면 센터서클·박스코너가 화면에서 사라짐** → H 실패 |
| 카메라 안정성 | ✅ 방송용 짐벌, 팬·줌하되 부드러움 | ⚠️ **손떨림** → H가 흔들려 2D 점이 떨리고 속도 지표 오염 |
| 겹침(occlusion) | ✅ 높은 위치라 덜함 | ⚠️ **낮은 카메라 = 심한 겹침** → 트랙 단절 급증 |
| 팀 분류 | 보통 (유니폼 색 조합에 따라) | ✅ 유니폼 통일 + 색 대비 확인 가능 |
| 라벨링 의미 | ⚠️ 모르는 선수 | ✅ **아는 선수** — 실제 전력분석 가치 |
| 저작권 | ⚠️ 재배포 불가 (내부 분석만) | ✅ 완전히 깨끗 |

**Stage 1의 주적은 "컷", Stage 2의 주적은 "화각과 흔들림"이다.** 아래 "분석 가능 구간 탐지"가 **둘 다를 하나의 메커니즘으로 처리한다.**

### 통합 개념: "분석 가능 구간(analyzable window) 탐지"

컷 감지와 화각 부족은 서로 다른 문제처럼 보이지만, **결과는 같다 — 좌표 변환을 믿을 수 없는 구간이 생긴다.**
따라서 하나의 판정으로 통합한다: **좌표 변환이 신뢰할 만한 연속 구간을 찾는다.**
(프리셋의 `cut_detection` 은 구간 경계를 만드는 추가 신호일 뿐, 별도 파이프라인이 아니다.)

**분석 가능 구간(analyzable window) 판정 조건 — 연속 프레임이 모두 만족:**
1. 경기장 키포인트 ≥ `min_keypoints` (호모그래피 계산 가능)
2. 직전 프레임 대비 H 변화량이 임계값 이하 (컷·튀는 프레임 배제 — **Stage 1의 컷을 여기서 잡는다**)
3. 화면 내 탐지 선수 ≥ `min_players` (**클로즈업·관중샷을 걸러내는 가장 강력한 필터**)
4. 구간 길이 ≥ `min_window_s`

이 조건을 만족하는 연속 구간을 자동 추출하고, **탈락 구간과 탈락 이유를 전부 기록해 웹에 표시한다.**
- Stage 1 예: `"18:04~18:09 — 선수 1명, 클로즈업 추정"`
- Stage 2 예: `"2:14~2:31 — 키포인트 평균 2.1개, 화각 부족(공 근접 팬) 추정"`

**중계 영상에서 이 필터가 잘 작동하는 이유:** 클로즈업·리플레이·관중샷은 짧고(2~6초) 선수가 적게 잡힌다.
반면 **빌드업을 담는 메인캠 롱샷은 15~40초까지 이어지고 선수가 많이 잡힌다.**
결과적으로 필터가 **분석 가치가 가장 높은 롱샷만 골라낸다.**

## 파이프라인 원리 (프로젝트의 심장)

```
경기 영상  (Stage 1: 프로 중계 / Stage 2: 스마트폰 통짜 촬영)
   │                          ↑ 차이는 PRESET 하나로 흡수
   ├─[0] 프레임 사전 스캔 (2fps, 빠르게)     → 키포인트 수 · 선수 수 · H 안정성 프로파일
   │      → 분석 가능 구간 M개 추출 (위 4조건)
   │      → 탈락 구간 + 이유 기록
   │
   ▼ 채택된 구간마다 아래를 독립 실행 (10fps 정밀 처리)
   │
   ├─[1] 선수·공 탐지 (YOLO)                → 화면 픽셀 좌표 박스
   ├─[2] 경기장 키포인트 탐지                → 센터서클·박스코너·라인교점의 화면 위치
   ├─[3] 유니폼 색 분류                      → A팀 / B팀 / GK / 심판
   │
   ├─[2]로 프레임별 호모그래피 H 계산          ← ★ 핵심이자 최대 위험
   │     H: 화면 픽셀 → 실제 경기장 미터 좌표
   │     팬·줌·손떨림 대응: H 파라미터를 시간축으로 스무딩 + 키포인트 부족 프레임은 보간
   │     실패 프레임은 버리고 warnings에 기록 (억지로 채우지 않는다)
   │
   ├─[1]의 박스 하단 중심점에 H 적용          → 선수의 실제 경기장 위치 (x m, y m)
   ├─ ByteTrack으로 프레임 간 동일인 추적      → track_id
   │
   └─ 좌표 시계열 → 격자 히트맵 · 궤적 · 속도 · 팀 형태 시계열 → analysis-bundle.json
```

**2단 처리(2fps 스캔 → 10fps 정밀)가 중요하다.** 전체 영상을 10fps로 돌리면 대부분이 버려질 구간이라 낭비다.
싸게 훑어 쓸 구간만 고른 뒤 거기에만 비용을 쓴다.

**공수 방향 정규화:** 전·후반이 섞이면 공격 방향이 뒤집힌다. 구간별로 공격 방향을 추정(또는 노트북에서 지정)하고,
지표는 **항상 "우측이 공격 방향"으로 정규화**해 저장한다. 안 하면 여러 구간의 히트맵을 비교할 수 없다.

### 짧은 구간이라 지표 정의가 바뀐다

30초 구간에 90분용 지표를 쓰면 무의미하다:

| 쓰지 않음 | 대신 쓰는 것 |
|---|---|
| 총 이동거리 | **순간 속도 시계열 · 최고속도 · 스프린트 구간(>20km/h)** |
| 90분 체류 히트맵 | **격자 히트맵 + 이동 궤적선** — 짧은 구간은 궤적이 훨씬 잘 읽힌다 |
| 시즌 평균 포지션 | **시작→종료 위치 벡터, 침투 방향·거리** |
| 정적 포메이션 | **팀 무게중심 이동 · 수비라인 높이 변화 · 팀 폭 신축** 시계열 |
| 점유율 | **구간 내 공간 점유 구역, 수비 블록 컴팩트니스 변화** |

`clip.py` 가 채택 구간만 잘라내므로 90분 원본을 통째로 옮길 필요는 없다.

⚠️ **`.gitignore` 에 `web/public/videos/` 를 반드시 넣는다.** 영상이 git에 올라가지 않게 하는 것이 저작권 안전선이자,
리포 용량이 터지지 않게 하는 장치다.

**상태 관리:** 백엔드가 없으므로 라벨링 결과는 `localStorage`. `try/catch`로 감싸고 값이 없어도 정상 렌더링되게 한다.
"라벨링 내보내기/불러오기" 버튼도 제공한다.

## 구현 단계

> **Stage 1 (프로 중계)로 Phase 0~5를 완주한 뒤, Stage 2 (아마추어)는 Phase 7에서 다룬다.**

### Phase 0 — 실현 가능성 검증 (Colab만, 웹 코드 없이) ⚠️ 가장 중요

**0-A. 통제된 조건에서 파이프라인 검증** — [`roboflow/sports`](https://github.com/roboflow/sports) 공개 샘플 클립으로 먼저 돌린다.
여기서 실패하면 **코드 문제**다(영상 문제가 아니다). 이 분리가 디버깅 시간을 크게 줄인다.

**0-B. 실제 중계 영상으로 판정** — 사전 스캔(2fps)만 먼저 돌려 프로파일을 뽑는다. `PRESET = "broadcast"`.

체크리스트:
1. **`git init` + private GitHub 리포 생성** → Colab에서 clone 되는지 (안 되면 이후 전부 막힌다)
2. **키포인트 탐지율 프로파일** — 프레임당 키포인트 개수의 시간 분포. 4개 이상인 프레임이 몇 %인가?
   (중계는 모델 학습 도메인이라 여기서 잘 나와야 정상. 안 나오면 **코드를 의심한다**)
3. **분석 가능 구간 개수** — 4조건 통과 구간이 몇 개, 총 몇 초인가?
   ★ **가장 불확실한 수치. 측정해 즉시 보고한다.** 중계는 컷이 잦아 채택률이 관건
4. **컷 경계가 맞는가** — 리플레이·클로즈업·관중샷이 실제로 탈락하는가? 롱샷이 살아남는가?
5. **선수 탐지** — 화면 먼 쪽(작게 보이는) 선수도 잡히는가? 프레임당 평균 몇 명인가?
6. **H 안정성** — 팬·줌 중 H가 얼마나 흔들리는가? 정지한 선수의 2D 점이 떨리는가?
   (`h_smooth_window` 값을 여기서 결정)
7. **팀 분류** — 두 팀 유니폼이 HSV로 갈리는가? GK·심판이 분리되는가?
8. **트랙 단절** — 한 선수가 평균 몇 개 트랙으로 쪼개지는가? (라벨링 부담 추산)
9. **속도 · GPU 할당** — T4가 배정되는가? 30초 구간 정밀 처리에 몇 초 걸리는가?

**산출물:** ① 키포인트/선수 수 시간 프로파일 그래프 ② 원본 위 박스 오버레이 영상 ③ 2D 탑다운 점 애니메이션.
노트북에서 인라인으로 확인한다.

**판정 분기:**
- **3번이 5개 이상** → 그대로 Phase 1 진행
- **3번이 1~2개** → 필터 완화(`min_window_s` 6초, `min_players` 5) 후 재측정. 그래도 적으면 **더 긴 영상**(풀경기 롱샷 다수)으로 교체
- **2번이 나쁨** → 중계 영상에서 이건 비정상이다. 0-A(샘플 클립)로 돌아가 **코드 버그를 먼저 찾는다**

### Phase 0.5 — 호모그래피 폴백 (Stage 2에서 필수가 되는 안전장치)

Stage 1(중계)에서는 보통 필요 없다. **Stage 2에서 반드시 필요해지므로 구조만 지금 잡아둔다.**

⚠️ **팬하는 영상에서는 수동 4점 캘리브레이션이 통하지 않는다** — 프레임마다 카메라가 달라지므로 매 프레임 4점을 찍을 수 없다.
따라서 폴백은 다음 순서로 구성한다:

1. **광학 흐름 H 전파 (`propagate.py`)** — 키포인트가 잘 잡힌 프레임을 앵커로 삼고,
   앵커 사이 구간은 `cv2.calcOpticalFlowPyrLK`(또는 ORB 특징점 매칭)로 **프레임 간 카메라 이동을 추적해 H를 연쇄 전파**한다.
   앵커에서 다시 만나면 누적 오차를 보정(양방향 전파 + 가중 평균)한다. **이 조건에서의 정석 기법이다.**
2. **팬이 적은 구간 우선 채택** — 프레임 간 H 변화가 작은 구간만 고른다. 확실하지만 채택 구간이 줄어든다.
3. **앵커 프레임 수동 지정** — 자동 키포인트가 0인 구간의 시작 프레임에서만 사용자가 4점을 찍고, 나머지는 1번으로 전파.

### Phase 1 — 노트북 완성 (구간 루프 + 데이터 계약 고정)

Phase 0의 단일 구간 처리를 **전체 구간 루프**로 확장하고 `analysis-bundle.json` 다운로드까지 동작시킨다.
- 셀 순서: 환경설치(git clone) → **프리셋 선택** → 영상 준비 → **2fps 사전 스캔 & 구간 탐지** → **구간별 루프**(탐지·추적·H·지표) → 공수 방향 정규화 → 번들 다운로드 → `clip.py` 로 채택 구간 클립 추출
- 파라미터를 **전부 `presets.py` 에서 읽는다.** 하드코딩된 임계값이 하나라도 남으면 Stage 2 전환 비용이 그만큼 늘어난다
- `window_index` 에 **탈락 구간과 이유를 전부 기록**한다 (채택률을 숨기지 않는다)
- `homography.frames_interpolated / frames_dropped` 를 구간마다 기록한다 (신뢰도 표시용)
- 이 시점에 `public/sample-analysis.json` + 구간 클립을 확보한다 → Phase 2를 실제 데이터로 개발

### Phase 2 — 웹 시각화

번들 드래그앤드롭 → **구간 선택 탭** → 대시보드.
- 구간 탭: `window_index` 기준. 채택 구간은 선택 가능, 탈락 구간은 회색 + 이유 표시 (**투명성이 신뢰를 만든다**)
- `SyncPlayer` : **원본 영상 ↔ 2D 레이더 나란히 동기화 재생.** 이 도구의 핵심 화면
- `source_profile` 배지 표시 — `handheld_elevated` 면 "좌표 신뢰도 낮음" 경고를 함께 노출
- `HeatmapGrid` : 12x8 바둑판, 셀 농도 = 체류 시간. 선수 선택 / 팀 전체 / 해상도 토글(12x8 ↔ 24x16)
- `Trajectory` : 궤적선. 시작(●) → 종료(▶), 속도에 따라 선 굵기·색 변화
- `ShapeChart` : 팀 폭·수비라인·컴팩트니스 시계열, 재생 위치와 동기화
- `players_in_frame` · `warnings` · `frames_interpolated` 를 화면에 항상 노출

### Phase 3 — 수동 라벨링 UI

`tracks[].thumbs` 로 트랙 카드 갤러리를 그린다. 선수 카드를 만들고 트랙 카드를 붙인다.
**끊긴 트랙 병합이 핵심 기능** — 겹침·가려짐 때문에 한 선수가 트랙 5~20개로 쪼개지는 것이 정상이다.
Phase 0 8번에서 측정한 단절 정도에 따라 UI를 조정한다 (단절이 심하면 시간축 + 위치 근접 기준 **자동 병합 제안** 기능을 추가).
Stage 2에서는 낮은 카메라 탓에 단절이 더 심해지므로 **자동 병합 제안을 Stage 1부터 만들어두는 편이 낫다.**
라벨링 변경 시 `metrics_by_track` 을 즉시 재합산해 히트맵·궤적이 갱신된다 (Colab 재실행 없음).

### Phase 4 — AI 분석 리포트

라벨링 반영된 지표 요약(원시 좌표 아님 — 5~15KB)을 `/api/report` 에서 Claude API로 보내 생성:
1. **선수별 움직임 평가** — 침투 방향·타이밍, 스프린트의 의미, 활동 영역, 동료와의 공간 중첩
2. **구간 전술 분석** — 이 공격/수비가 어떻게 전개됐는지, 팀 폭 신축·수비라인 이동·컴팩트니스 변화의 해석, 문제점과 개선점

시계열은 배열 원본이 아니라 **구간 요약**으로 압축 전달 (예: "0~8초 폭 42m → 8~15초 31m로 좁힘").

구현 시 **`claude-api` 스킬을 반드시 로드**해 최신 모델 ID·스트리밍·프롬프트 캐싱을 확인한다.
프롬프트에 다음 제약을 명시해 AI가 과단정하게 말하지 않도록 한다:
- 수치는 CV 추정치이며 오차가 있다
- `players_in_frame` 이 11 미만이면 화면에 안 잡힌 선수가 있으므로 팀 전체를 단정하지 말 것
- `warnings` / `frames_interpolated` 가 큰 구간을 근거로 삼지 말 것

### Phase 5 — Stage 1 마무리

로컬 `npm run dev` 로 전체 흐름이 끊김 없이 도는 상태를 만든다.
- `.env.local` 에 `ANTHROPIC_API_KEY`, `.gitignore` 에 `web/public/videos/` 확인
- `README.md` 에 "Colab 노트북 실행 → 번들 다운로드 → 웹에 드래그" 3단계 사용법 기록
- Vercel 배포는 **선택** — 하려면 `public/videos/` 를 제외하고 `sample-analysis.json` 만 담아 올린다

### Phase 6 — ★ Stage 2 전환 (아마추어 리그 실사용)

**여기서 웹은 한 줄도 건드리지 않는다.** 노트북 쪽만 손본다.

1. `presets.py` 에 `handheld_elevated` 값을 실측으로 채운다 (구장 규격 포함)
2. **Phase 0-B와 동일한 사전 스캔을 아마추어 영상으로 재실행** → 키포인트율·채택 구간 수 측정
3. 결과에 따라 분기 — **여기서 정직하게 갈린다:**
   - **키포인트 4개 이상 프레임 60%+** → 그대로 진행
   - **20~60%** → Phase 0.5 광학 흐름 전파 활성화
   - **20% 미만** → 자동화 불가. 세 선택지를 **즉시 보고하고 사용자가 고르게 한다:**
     (a) 화각이 넓은 구간만 소수 채택해 규모를 줄인다
     (b) **키포인트 모델 파인튜닝** — 이 구장·이 카메라 각도 프레임 30~50장 라벨링 (Roboflow, 반나절~2일). **정확도 레버가 가장 크다**
     (c) 촬영 조건을 바꿔 재촬영 (아래 촬영 가이드) — **비용 대비 효과가 가장 크다**
4. 팀 분류 HSV 임계값을 실제 유니폼 색 조합으로 조정
5. 트랙 단절이 심해지면 Phase 3의 자동 병합 제안 기능을 강화

## 촬영 가이드 (Stage 2 정확도 레버가 가장 큰 항목)

다음 촬영이 가능하다면 이것만으로 성공률이 크게 올라간다. Phase 6 결과가 나쁠 때의 1순위 대응책이다.

1. **최대한 높은 곳** — 스탠드 상단, 언덕, 사다리. 카메라가 높을수록 겹침이 줄고 모델 학습 도메인에 가까워진다
2. **삼각대 고정, 팬 최소화** — 공을 따라가지 말고 경기장을 고정으로 담는다. 이게 가장 중요하다
3. **경기장 전체 또는 최소 절반 + 랜드마크** — 화면에 **센터서클이나 페널티박스가 항상 하나는 보이게** 한다
4. **미드필드 라인 연장선 위치** — 사이드라인 중앙에서 촬영하면 좌우 왜곡이 대칭이 되어 호모그래피가 안정적이다
5. **1080p 30fps 이상, 손떨림 보정 ON**
6. **경기장 실측** — 가로·세로 미터를 재둔다 (거리·속도 지표 정확도가 여기서 결정된다)

## 검증 방법

**Phase 0 (가장 중요한 관문) — Colab에서**
- 키포인트/선수 수 시간 프로파일 그래프를 보고 **채택 가능 구간 비율을 숫자로 확인** (이게 판정 근거다)
- `overlay.mp4` (원본 위 박스·트랙 ID)와 `radar.mp4` (2D 탑다운)를 인라인 재생
- 판정 기준: 선수 대부분이 매 프레임 잡히고, 2D 점이 떨리지 않고, **경기장 경계를 벗어나지 않을 것**
- **정지 선수 테스트**: 거의 움직이지 않는 선수(GK 등)를 골라 2D 점이 제자리에 머무는지 확인 → H 안정성의 직접 증거

**Phase 1** — `analysis-bundle.json` 이 데이터 계약과 일치하는지 확인
- `window_index` 의 채택/탈락 개수와 이유를 원본 영상에서 2~3개 직접 대조
- 여러 구간 히트맵을 나란히 놓고 공격 방향이 통일됐는지 (정규화 검증)
- 번들 크기가 10MB를 넘으면 썸네일 품질·좌표 정밀도 조정

**Phase 2~4** — 웹
```bash
cd /Users/song/Desktop/Song/Portfoilo/football/web && npm run dev
```
`.claude/launch.json` 에 `web` 항목을 등록하고 preview 도구로 브라우저 검증:
샘플 로드 → 구간 탭 → **동기화 재생(영상과 레이더 시간이 맞는지)** → 히트맵 → 궤적 → 라벨링 저장 후 히트맵 변화 → AI 리포트 스트리밍.
콘솔 에러 · **SVG y축 방향 뒤집힘** · 다크모드 · 모바일 폭을 함께 확인.

**정확도 sanity check (수동)**
- 선수 1명을 골라, 영상에서 눈으로 본 움직임과 궤적선 모양이 일치하는지
- 이동거리가 상식 범위인지 (30초 구간 → 대략 50~150m)
- 최고속도가 30km/h를 넘으면 좌표 튐 → 스무딩 파라미터 조정
- 궤적선이 경기장 경계를 벗어나면 호모그래피 오류 → Phase 0.5 폴백으로 전환

**Phase 6 (Stage 2 전환) — 회귀 검증**
- 프리셋만 바꿔 Stage 1 영상을 다시 돌렸을 때 **이전과 동일한 결과가 나오는지** 확인 (프리셋 분리가 제대로 됐다는 증거)
- 아마추어 영상 지표를 Stage 1과 같은 sanity check로 검증 — 값이 비상식적이면 H 문제이지 지표 문제가 아니다
